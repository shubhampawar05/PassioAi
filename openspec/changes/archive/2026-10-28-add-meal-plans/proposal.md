# Proposal

## Why

After logging food and asking the advisor, the next demo step is planning ahead: a few days of meals that fit the user's profile, a shopping list, and one-click logging of a planned meal. Passio's meal-plan routes were verified live on 2026-10-28 (preview, regenerate-by-rejecting, full plan, humanized shopping list). The full plan returns recipes with per-recipe macros, so the app can show and log them without inventing nutrition values.

## What Changes

- **Meal-plan preview.** The app generates a 1–7 day plan of meal names (breakfast, lunch, dinner, snack) from the nutrition profile plus optional short notes, via Passio `generateMealPlanPreview`. The default is 3 days.
- **Reject and regenerate.** The user marks meals they don't want, and only those are regenerated by resending the preview with `rejected: true`. This matches the documented and live-verified workflow.
- **Full plan.** The user approves the preview, and the app generates the full plan via Passio `generateMealPlan` as a background job with status polling. It shows recipes, ingredients, preparation steps, and Passio's per-recipe and per-day macros, plus the shopping list.
- **Shopping-friendly list.** Optionally converts the plan's shopping list via Passio `humanizeShoppingList`.
- **Log a planned meal.** Creates a food-log entry from a recipe's stored Passio macros (input type `meal_plan`), computed server-side from the saved plan. It then appears in the diary and daily totals.
- **Saved plans.** Plans are kept in PostgreSQL. The user can list, view, and delete them.
- **Not included:** `regenerateMeals` and `updateMealPlanShoppingList` (request and response formats are undocumented), and affiliate grocery links (commerce is out of scope).

## Capabilities

### New Capabilities

- `meal-plans`: generating, refining, approving, viewing, and deleting profile-based meal plans via Passio, including the shopping list and background generation.

### Modified Capabilities

- `food-log`: adds input type `meal_plan` and logging an entry from a saved meal-plan recipe. This modifies the `Supported entry input types` requirement introduced by `add-label-and-camera-barcode-scan`.

## Impact

- **Depends on:** `add-nutrition-profile-and-advisor` (profile and scope guard) and `add-label-and-camera-barcode-scan` (the input-types requirement). Both must be implemented and archived first.
- **API:** `/api/meal-plans` routes, a `MealPlan` Prisma model and migration, an in-process job runner, and the enum value `meal_plan`.
- **Web:** a "Meal plans" view with a preview editor, generation progress, plan detail, shopping list, and a "Log this meal" action.
- **Passio cost, measured live for 2 days:**
  - preview: ~5,000 tokens
  - regenerate: ~5,300 tokens
  - full plan: **~133,000 tokens**, taking 14 s (the docs say 1.5–6 min)
  - shopping list: ~2,600 tokens

  A 7-day plan is expected to cost several hundred thousand tokens, so the UI states the cost class before generating.
